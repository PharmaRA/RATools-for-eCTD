# ADR-0001：当前仅支持 local-only 单实例部署

- 状态：Accepted
- 日期：2026-08-10
- 决策：D-02
- 关联发现：[F-09、F-10](../reviews/2026-08-10-code-review-and-development-roadmap.md#f-09-p2部署相关-浏览器共享-api-key-与客户端可写审计不构成多用户安全模型)

## 1. 决策

RATools-for-eCTD 当前只支持以下部署形态：

- 单个受信任操作人员；
- 浏览器、API 和文件工作区位于同一台受控主机；
- 只运行一个 API/worker 实例；
- HTTP 服务只监听 loopback 地址，不经反向代理、局域网或公网暴露；
- PostgreSQL 只允许该主机访问，不向不受信任网络发布端口；
- 主机账户、数据库账户、工作区和发布目录均由同一安全边界控制。

`local-only` 是部署限制，不是完整的用户身份模型。当前 API Key 只能阻止未携带共享凭据的请求，不能区分用户，也不能在浏览器中保持机密。审计记录目前也不能提供多用户环境中的不可抵赖性。

shared deployment、多用户访问、远程浏览器、水平扩展和高可用均不在当前支持范围内。它们必须作为独立安全里程碑完成本文第 7 节的退出条件后，才能改变本 ADR。

## 2. 背景

当前实现包含以下架构事实：

- 前端通过 `VITE_API_KEY` 把共享 API Key 放入浏览器构建环境；任何能够加载或检查客户端的人都可读取它。
- API 使用全局 API Key fallback policy，但认证主体恒为 `api-key-client`，没有用户身份或角色。
- `POST /api/audit-logs` 接受客户端提供的 `Actor` 和 `Details`，普通客户端能够伪造审计主体和内容。
- 发布命令先写数据库，再进入有界的进程内 Channel；队列不跨进程持久化。
- 启动恢复会把所有活动作业视为上一个进程的遗留任务；该假设只在单实例下成立。
- 每个 PostgreSQL API 进程启动时直接执行 EF Core migration。

因此，现有实现不能通过配置一枚更长的 API Key 变成安全的共享服务，也不能通过同时启动多个实例获得安全的横向扩展。

## 3. 资产和信任边界

需要保护的资产包括：

- 监管申报文档、PDF 正文和文档元数据；
- application/sequence 工作区和生命周期关系；
- 发布产物、校验报告、校验和与压缩包；
- PostgreSQL 中的业务状态、作业状态和审计记录；
- API Key、数据库凭据和主机文件权限。

当前唯一信任边界是受控本地主机及其操作系统账户。浏览器不是秘密存储区，API Key 也不是用户身份。进入主机的恶意代码、浏览器扩展、XSS、被窃取的本地凭据以及具有本地读取权限的其他账户，均视为能够以该操作人员身份调用 API。

## 4. 威胁模型

| 威胁 | 当前控制 | 残余风险 / local-only 限制 |
| --- | --- | --- |
| 未授权调用业务 API | 全局 API Key 认证；固定时间比较 | Key 可从浏览器构建产物或本机流量中取得，不能用于不受信任客户端或网络 |
| 伪造审计主体和内容 | 业务服务会写入部分系统审计事件 | 公共审计写入口仍接受客户端 `Actor`；审计不可作为多用户不可抵赖证据 |
| 越界读写或删除文件 | 允许根白名单、工作区归属检查、reparse 防护、服务端发布根、破坏性操作开关 | 本地高权限账户仍可绕过应用直接访问文件；允许根和主机 ACL 必须正确配置 |
| API Key 重放或中间人窃取 | 仅在请求头中传递 Key | 当前本地 HTTP 没有传输层身份保证；只能绑定 loopback，禁止跨主机明文访问 |
| 多实例重复执行发布 | 单活动作业数据库约束；单进程有界队列 | 没有 claim lease、heartbeat、instance owner 或幂等执行；不得运行第二实例 |
| 启动时误回收仍在执行的作业 | 单实例启动顺序先恢复、后启动 worker | 第二实例会把第一实例的活动作业标记失败；恢复逻辑只适用于单实例重启 |
| 并发数据库迁移 | API 启动时自动迁移 | 多实例并发启动不受支持；shared/HA 部署必须改为单独 migration job |
| 资源耗尽 | 上传上限、审计分页上限、发布队列容量和 backpressure | 单机磁盘、CPU、数据库连接和认证失败请求仍可能耗尽资源；主机不得暴露给不受信任流量 |
| 主机或本地账户失陷 | 操作系统账户、文件 ACL、数据库凭据和备份策略 | 应用无法防御已控制受信任主机的攻击者；需要通过主机安全与事件响应处理 |

## 5. local-only 运行要求

满足以下全部条件才属于受支持部署：

1. Kestrel 只绑定 `127.0.0.1`/`localhost`，不得绑定 `0.0.0.0`、局域网地址或公网地址。
2. 只运行一个 RATools API 进程；不得通过容器副本、进程管理器或负载均衡器启动第二实例。
3. PostgreSQL 只监听 loopback 或受限本机通道；主机防火墙不得允许外部访问数据库端口。
4. 使用随机、非默认 API Key；不得提交真实 Key、数据库密码或工作区凭据。
5. `Security:AllowedWorkspaceRoots` 只包含专用目录；工作区、上传和发布目录使用最小主机文件权限。
6. 非必要时保持 `Security:AllowDestructiveOperations=false`。
7. 主机启用磁盘加密、补丁、恶意软件防护和访问审计，并对数据库与工作区进行受控备份。
8. 不把开发用 Vite 前端、Swagger 或默认 PostgreSQL 凭据当作生产安全边界。

仓库当前的开发配置和 Compose 文件用于本机开发，不代表加固后的部署配置。Phase 3 的后续工作必须在配置层显式执行上述 loopback、单实例和非默认凭据约束。

## 6. 后果

采用该决策后：

- 可以继续改进单机工作流，而不误称当前系统已经具备多用户安全性或高可用能力。
- 文档、配置默认值、测试和支持声明都必须以单用户、单实例、loopback 为前提。
- 在 shared milestone 完成前，发现远程访问或第二实例时应启动失败，而不是降级为“尽力而为”。
- 公共客户端审计写入口仍需内化；服务端业务流程应生成审计主体和事件。
- 持久作业仍需迁移到数据库 claim/lease 模型；仅增加 Channel 容量不能解除单实例限制。

## 7. shared deployment 退出条件

只有满足以下条件并由新的 ADR 取代本文，才能支持 shared deployment 或多实例：

1. 使用 OIDC 或等价的服务端 session 身份体系，并定义最小角色与授权矩阵。
2. 对 cookie/session 流程实施 CSRF 防护，对浏览器输入实施相应的 XSS 与安全响应头控制。
3. 审计 actor 从已认证服务端身份派生；删除或内化公共审计创建端点。
4. 发布命令使用数据库持久 outbox/queue，支持原子入队、claim lease、heartbeat、worker instance ID、可控重试和幂等键。
5. 只回收租约过期的作业，并有双实例集成测试证明不会重复执行或误回收。
6. 数据库 migration 从 API 启动路径移出，作为部署阶段的单独单实例任务执行。
7. 为 TLS、反向代理信任、密钥轮换、速率限制、集中日志、备份恢复和事件响应提供运行手册。
8. 完成针对远程不受信任客户端、普通用户、特权用户和失陷 worker 的更新威胁模型与安全评审。

## 8. 复审触发条件

以下任一情况出现时必须立即复审本 ADR：远程浏览器访问、局域网/公网监听、第二 API 实例、反向代理、不同权限用户、集中式部署，或将审计记录用于用户行为归责。
