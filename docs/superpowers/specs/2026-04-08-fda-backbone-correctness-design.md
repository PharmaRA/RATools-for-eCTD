# FDA Backbone Correctness Design

**Goal**

Improve the current eCTD publish backend so generated backbone XML is more structurally aligned with FDA eCTD v3.2.2 conventions without introducing a full schema-ready rewrite.

## Scope

This design is intentionally narrow. It improves backbone correctness in the current application-layer XML generator and validation workflow while leaving lifecycle, full section dictionaries, and database schema unchanged.

In scope:

- Tighten section path syntax and output semantics
- Tighten backbone root and leaf metadata
- Add validation rules that specifically protect backbone correctness
- Keep publish output paths and XML href values strictly consistent

Out of scope:

- Full FDA section dictionary coverage
- Full lifecycle cross-sequence validation
- DTD/XSD/Schematron compliance work
- Frontend changes
- Domain model or database schema redesign

## Selected Approach

Use the existing `BackboneService`, `PublishOutputNaming`, and `SequenceValidationService` as the main integration points.

This avoids a large refactor and keeps risk low:

- `BackboneService` remains the single XML assembly point
- `PublishOutputNaming` remains the single source of truth for published artifact paths
- `SequenceValidationService` remains the place where backbone-related errors and warnings are enforced before publish

## Backbone Structure Changes

### Root Node

The backbone root continues to use the existing `ectd:ectd` element, but the emitted metadata is tightened and made stable:

- `xmlns:ectd`
- `xmlns:xlink`
- `dtd-version="3.2.2"`
- `applicationNumber`
- `sequenceNumber`
- `submissionType`
- `region`

The root keeps these child nodes:

- `ectd:applicant`
- `ectd:sequenceDescription`

This remains a minimal FDA-oriented shape rather than a full schema-ready root.

### Section Paths

Section paths must satisfy the following minimal CTD grammar:

- First segment must be one of `m1`, `m2`, `m3`, `m4`, `m5`
- Remaining segments may be numeric or standard ICH letter segments such as `p`, `s`, `r`, and `a`
- Paths such as `m5..1`, `.m5.1`, `module5.3`, and `m5.q.1` are invalid

The XML section tree remains hierarchical, but section `id` values use cumulative paths instead of local fragment values.

Example:

```xml
<ectd:section id="m5">
  <ectd:section id="m5.3">
    <ectd:section id="m5.3.5">
      <ectd:section id="m5.3.5.1">
      </ectd:section>
    </ectd:section>
  </ectd:section>
</ectd:section>
```

### Leaf Output

Each leaf is tightened to the following minimal shape:

```xml
<ectd:leaf
  id="..."
  operation="new"
  xlink:href="documents/{documentIdN}_{fileName}"
  xlink:type="simple"
  checksum-type="md5">
  <ectd:title>...</ectd:title>
  <ectd:fileName>...</ectd:fileName>
  <ectd:mimeType>...</ectd:mimeType>
  <ectd:checksum>...</ectd:checksum>
</ectd:leaf>
```

Rules:

- `id` remains the placement id
- `operation` remains normalized to lowercase
- `xlink:href` must always match the published file path generated by `PublishOutputNaming`
- `xlink:type` is fixed to `simple`
- `checksum-type` is fixed to `md5`
- `title` falls back to `document.FileName` when no explicit placement title is provided

## Validation Changes

### Errors

These block publish:

- `INVALID_SECTION_PATH`
  - Section path fails minimal CTD grammar
- `UNSUPPORTED_OPERATION_VALUE`
  - Operation cannot be mapped to supported leaf operations
- `MISSING_LEAF_CORE_METADATA`
  - Leaf generation would be missing file name, media type, checksum, or published href
- `DUPLICATE_PUBLISHED_DOCUMENT_PATH`
  - Two documents resolve to the same publish-relative output path
- `PUBLISHED_DOCUMENT_NOT_FOUND`
  - Generated href would not resolve to a published artifact

### Warnings

These do not block publish:

- `TITLE_FALLBACK_USED`
  - Placement title is absent and file name will be used in backbone output
- `SECTION_DEPTH_SHALLOW`
  - Path is legal but too shallow, e.g. only `m5`
- `NON_STANDARD_SECTION_PATTERN`
  - Path is legal but structurally atypical for expected FDA usage
- Existing warning rules remain valid where they support backbone quality

### Validation Profiles

The existing `strict / relaxed` profile mechanism remains in place.

- `strict`
  - Enables all backbone-focused warnings and errors
- `relaxed`
  - Keeps blocking errors but suppresses or reduces some warnings

## File-Level Implementation Boundaries

Primary files to modify:

- `src/RATools.Application/Publishing/BackboneService.cs`
- `src/RATools.Application/Publishing/PublishOutputNaming.cs`
- `src/RATools.Application/Validation/SequenceValidationService.cs`
- `tests/RATools.Application.Tests/Publishing/BackboneServiceTests.cs`
- `tests/RATools.Application.Tests/Validation/SequenceValidationServiceTests.cs`
- `scripts/smoke-test.ps1`

Files intentionally not targeted in this change:

- Domain model redesign files
- EF Core schema files
- Frontend files
- Full section dictionary sources

## Verification Strategy

Add and maintain test coverage for:

- Unique published href generation when file names collide
- FDA-oriented backbone root and leaf metadata
- Cumulative section id generation
- Invalid section path blocking
- Title fallback warning semantics
- Smoke test assertions for new backbone metadata and href behavior

## Expected Outcome

After this change, the backend should still remain a minimal FDA-oriented implementation, but backbone output will be more deterministic, more semantically stable, and less likely to produce structurally invalid or misleading eCTD artifacts.
